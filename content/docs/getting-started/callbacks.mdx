<Brand /> sends real-time notifications to your application when important
events occur — payout state changes, beneficiary verification completes, and so
on. Each notification is an **HTTP POST** request to your configured endpoint
with a JSON payload.

## How to configure webhooks

<Steps>
<Step>
### Sign in to your account

Sign in to the <DashboardLink>merchant dashboard</DashboardLink>.
</Step>

<Step>
### Open the webhooks panel

Navigate to **Dashboard → Settings → Security → Webhooks**.
</Step>

<Step>
### Register endpoints

Enter the public HTTPS URL for each webhook type you want to receive.
</Step>

<Step>
### Copy the signing secret

Copy the **shared signing secret** from the same Webhooks section and store it
in your secret manager. You will need it to verify incoming requests.
</Step>
</Steps>

## What you'll receive

- **Method:** `POST`
- **Content-Type:** `application/json`
- **Header:** `X-Signature`
- **Payload:** JSON

You can register a **separate URL per event type** (payout, bank-beneficiary, UPI-beneficiary), so different event families can be delivered to different endpoints.

## Delivery, acknowledgement & retries

- **Acknowledgement:** respond with any **HTTP 2xx**. A response body is **not** required — the status code alone acknowledges receipt.
- **Timeouts:** ~**10 s** read/response, ~**1 s** to connect.
- **Retries:** up to **2** retries (3 attempts total), starting at ~**0.5 s** with exponential backoff (≈0.5 s, then ≈1 s).
- **After the final attempt:** delivery is **best-effort** — if all attempts fail, the event is **not** re-queued and there is no dead-letter replay.

Because delivery is best-effort, treat callbacks as a **fast notification, not a guaranteed ledger**: keep your handler **idempotent** (dedupe on `payout_id` / `client_reference_id`), return `2xx` quickly and process asynchronously, and **reconcile via the status APIs** as the source of truth.

## Payout status update

Payout callbacks are delivered on the **terminal** events `succeed`, `refunded`, and
`rejected` (the in-flight `processing` state is **not** delivered as a webhook). The body
carries these **10 fields**:

```json
{
  "payout_id": "TID251224095503GMA37C3EE",
  "bank_currency": "inr",
  "beneficiary_id": "WBID251224092108GMC9757E",
  "client_reference_id": "BIGBULL0001-2",
  "amount": "100.0",
  "fee": "0.0",
  "payout_status": "succeed",
  "bank_transaction_id": "UTR2412240955030001",
  "status_code": "COMPLETED",
  "status_message": "Payout Completed"
}
```

On a **rejected** payout the same 10 fields are sent with:
`payout_status: "rejected"`, `bank_transaction_id: null`,
`status_code: "EXT: <reason> | Auto rejected"`, `status_message: null`.

<Callout type="info">
The payout callback does **not** include `sender_name`, `created_at`, or `completed_at`
(those appear on the `GET /account/payouts/status` response, not the webhook), nor any
sender-identity or OTC fields. Correlate to that data via `client_reference_id` / `payout_id`.
</Callout>

## Bank-account beneficiary status update

Core body is **8 fields**; the four `verification_data_*` fields are added **only when a
penny-drop verification ran**. Example (verified):

```json
{
  "beneficiary_id": "WBID251024044324GM560AAE",
  "bank_currency": "inr",
  "bank_ifsc_code": "SBIN0000112",
  "account_number": "1234567890",
  "account_holder_name": "AMIT DOE",
  "status_code": "VERIFIED",
  "status_message": "Verification Completed",
  "verification_status": "active",
  "verification_data_bank_ref_no": "BRN-20251024T044324777-93VQR9",
  "verification_data_bank_beneficiary_name": "USER_NAME",
  "verification_data_bank_transaction_remark": "Transaction Successful",
  "verification_data_bank_transaction_status": "VERIFIED"
}
```

On a **rejected** verification, `verification_status: "rejected"`, `status_code` carries the
reason (e.g. `ACCOUNT_BLOCKED`, `INVALID_ACCOUNT_NUMBER`), and the `verification_data_*` fields
are `null` except `verification_data_bank_transaction_status: "FAILED"`.

## Setup requirements

- Provide a **public HTTPS callback URL** for each webhook type.
- Your endpoint must accept **HTTP POST** requests with a JSON body.
- A **webhook signing secret** is issued from
  **Dashboard → Settings → Security → Webhooks** for signature verification.

## Signature verification

Every callback request includes an `X-Signature` header. You **must verify**
this signature before processing the payload.

<Callout type="warn">
Verify over the **raw request body exactly as received** — do **not** `JSON.parse`
and then re-serialize. Re-stringifying can change byte-level details (key order,
whitespace, unicode escaping) and cause verification to fail even for a genuine
callback. Capture the raw body **before** any JSON parsing.
</Callout>

The signature is `HMAC-SHA256(webhook_secret, rawBody)`, hex-encoded:

```
X-Signature = HMAC_SHA256(webhook_secret, <raw request body bytes>)   // lowercase hex
```

### Verification (JavaScript / TypeScript)

```ts title="verify.ts"
import crypto from "crypto";

// `rawBody` is the exact request body string as received (before JSON.parse).
export function verifySignature(signature: string, rawBody: string, secret: string): boolean {
  const computed = crypto
    .createHmac("sha256", secret)
    .update(rawBody, "utf8")
    .digest("hex");

  return crypto.timingSafeEqual(
    Buffer.from(signature.trim().toLowerCase(), "hex"),
    Buffer.from(computed, "hex"),
  );
}
```

## Security considerations

- Store callback secrets securely (secret manager, not source control).
- Always use **timing-safe** comparison when verifying.
- Reject the webhook if signature verification fails.
- Do not trust webhook payloads without verification.
- Treat webhooks as **event triggers** and use the status APIs as the source of truth.
